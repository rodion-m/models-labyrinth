# Benchmark IDs: aliases, composites, and opaque claims

Research cut: 2026-08-26. Source snapshot: [`models_db.json`](../../models_db.json), generated `2026-08-26T16:34:24.006Z`, 10,360 models, 399 benchmark definitions. The extraction rule was the literal `benchmark_id` field, deduplicated, filtered to the four requested prefixes. It produced 174 IDs.

This is an identity and interpretability map, not a leaderboard. A value in `models_db.json` is not treated as a canonical benchmark result merely because the ID resembles a published benchmark. The database itself records `benchgecko` observations as “Secondary aggregator; consult source methodology.” Artificial Analysis indices are composites; `score.*` values are BenchLM display fields. Where I could not verify a public owner, release, task set, or evaluator from a primary source, the table says so explicitly.

## Reading the table

- **Canonical** means a public benchmark or competition with a primary owner/source and a reasonably defined task set.
- **Alias / snapshot** means the ID can be mapped to a benchmark family, version, harness, subset, or language slice, but the ID alone does not identify all evaluation settings.
- **Aggregate / index** means it combines other measurements or a live preference pool; it is not an independent task set.
- **Model/provider claim** means the field is an externally reported result, private/internal evaluation, vendor mirror, or opaque metric. It must not be used as a general model capability fact without the exact run, model version, prompt, tool policy, scaffold, and evaluator.
- “Current” means the latest version I could verify in the cited primary source as of the research cut, not necessarily the version represented by the database row. “Not encoded” means the ID has no version token, so old and new runs can be mixed.

## Use/ignore rules for agents

1. **Use canonical rows only when protocol matches the task.** Require the primary owner/version, task split, prompt/shot policy, tool policy, evaluator, and metric direction. A benchmark name alone is insufficient.
2. **Treat aliases as one evidence family.** Do not count `benchgecko.mmlu`, `hf-mmlu-pro`, `helm-mmlu-pro`, `oc-mmlu-pro`, and `artificial_analysis.*` as independent votes. They may share the same questions or be composites of one another.
3. **Keep agent/system results separate from model results.** For OSWorld, Web/desktop agents, Aider, SWE-bench, Terminal-Bench, BALROG, CyBench, APEX, DeepResearch, PostTrainBench, and similar rows, preserve model, harness/scaffold, tools, environment, retries, turn/token budget, and judge/evaluator. Never use them to recommend a base model without those fields.
4. **Do not mix versions or slices.** In particular: ARC-AGI-1/2/3; FrontierMath legacy/2025/v2; LiveBench releases; HLE closed-book/tools; MMLU/MMLU-Pro/Redux/MMMLU; OSWorld/original/Verified/2.0; SWE-bench Verified/Multilingual/Multimodal/Pro; Terminal-Bench 2.0/2.1/3; Video-MME v1/v2 and subtitle variants.
5. **Ignore aggregates and opaque fields for ranking or recommendations.** This includes all `score.*`, `avg_score`, `jp-overall`, `livebench-overall`, AA indices, arena Elo, `aa-quality-index`, unknown MCP/SEAL/HF/OC claims, and every `external.*` row lacking a public primary protocol. They may be displayed as provenance-labeled context only.
6. **Never infer metric direction from a friendly name.** “Solved,” “completion,” “coverage,” “revenue,” “Elo,” and “score” have different units and incentives. Store the documented direction and unit; otherwise mark the field opaque and ignore it.
7. **Never use private/provider claims to make safety or cyber decisions.** Cyber rows may reflect authorized internal tests, but without task provenance, safety controls, repeats, and evaluator disclosure they cannot responsibly support a model selection or risk conclusion.
8. **Use duplicate families for coverage, not vote counting.** For coding/agentic recommendations prefer at most one matched row from each construct family (e.g., one repository-fixing row, one terminal row, one real-computer row), then validate with a local task-relevant evaluation. For reasoning/knowledge use distinct constructs rather than a large number of legacy MCQ aliases.
9. **Report uncertainty explicitly.** If a value cannot be tied to a canonical version and reproducible protocol, label it “unresolved/opaque,” show the raw ID and source URL, and do not fill in missing version, construct, scaffold, metric, or replacement information.
